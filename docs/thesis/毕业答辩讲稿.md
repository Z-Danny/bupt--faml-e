## 正式讲稿

各位老师好，我的毕业设计题目是《面向大学生的 AI 心理健康支持平台 Famlée 的设计与实现》。下面我将从选题背景、系统设计、关键实现、系统演示、测试结果和总结展望几个方面进行汇报。

首先是选题背景。大学生在学习、就业、人际关系和自我认同等方面，经常会遇到比较持续的情绪压力。但现实中，很多同学在情绪刚出现波动时，并不会马上去预约心理咨询。一方面是因为心理咨询资源有限，另一方面也是因为很多情绪表达比较碎片化，可能只是某一天焦虑、难过、烦躁，或者想找一个不会评判自己的对象倾诉。

因此，本项目的定位不是替代专业心理咨询，也不做医学诊断，而是设计一个面向大学生日常场景的 AI 心理健康支持平台。它的目标是提供低门槛的情绪表达入口、连续的情绪记录，以及更有结构的 AI 陪伴式支持。

Famlée 主要包含四类功能。第一是 AI 疗愈对话，系统提供三种不同风格的人格角色：治愈系 Melty、理性系 Logic 和趣味系 Spark，分别对应 ACT 接纳承诺、CBT 认知梳理和轻量幽默缓冲。第二是情绪日记，用户可以记录文字、图片和音频，系统可以生成摘要并保存到数据库。第三是 Mood 日历，用来把用户的情绪记录可视化，帮助用户回看近期状态。第四是校园活动和后台管理模块，用来展示校园心理相关资源，并为后续管理端数据统计留下接口。

在技术实现上，系统前端使用 React 19、TypeScript 和 Vite 构建，样式使用 Tailwind CSS。后端采用 Node.js 和 Express，自托管 API 服务负责用户鉴权、文件上传、AI 代理和数据持久化。数据库使用 PostgreSQL，主要保存用户、日记、聊天会话、聊天消息、情绪事件和阶段反思等数据。AI 部分通过后端调用火山引擎 Ark / 豆包的 OpenAI-compatible chat completions 接口，并使用 Server-Sent Events 实现流式回复。

这里有一个比较重要的设计点：前端不会直接接触模型 API Key，也不会直接调用大模型。所有 AI 请求都经过 Express 后端，由后端完成鉴权、历史消息拼接、图片转换、模型调用和结果落库。这样可以保证密钥安全，也便于后续统一加入安全策略和数据分析。

在 AI 对话层面，我没有只做简单的 prompt 拼接，而是设计了 Agent + Skill Pipeline。用户输入进入后，会先经过情绪识别 Skill，识别焦虑、难过、生气、开心和平静等状态；然后经过安全保护 Skill，判断是否存在高风险表达；再经过隐私保护 Skill，对邮箱、手机号、身份证、学号等敏感信息进行脱敏；之后系统根据用户选择的人格、当前情绪和工具按钮，路由到不同的支持策略 Skill，比如 CBT 引导、正念呼吸、情绪接纳、证据检验或价值澄清。最后再组合成模型的 system prompt，生成符合当前场景的流式回复。

刚才视频展示的是用户端的主要使用流程。可以看到，用户进入系统后，可以先选择符合自己当前状态的人格角色；在对话中，AI 会以流式方式逐步回复，减少等待感；如果用户不想直接描述复杂问题，也可以使用系统提供的快捷心理工具来进入结构化引导。情绪日记和 Mood 日历则用于把一次性的倾诉沉淀成连续记录，帮助用户回顾自己的情绪变化。

为了验证系统效果，我做了几组测试。第一组是情绪识别测试，使用 100 条样本，覆盖平静、开心、焦虑、难过和生气五类情绪。测试目标不是看模型回复是否自然，而是看它能否稳定输出后续系统可以使用的结构化字段，例如情绪标签、风险等级和推荐 Skill。结果显示，普通大模型直接回复虽然可以自然安慰用户，但结构化输出不稳定；而 Famlée 的情绪识别 Skill 可以稳定生成用于路由的中间结果。

第二组是支持回复质量对比测试。我构建了 20 条大学生日常情绪表达场景，对比普通大模型直接回复和 Famlée Agent 框架回复。评价维度包括情绪贴合度、策略匹配性、非评判性、继续倾诉意愿和记录反思价值。从测试结果看，Famlée 在策略匹配性和记录反思价值上更有优势，因为它不是直接给一段泛化安慰，而是先识别情绪，再选择合适的支持策略，并生成可沉淀到后续情绪记录中的信息。

第三组是安全风险场景测试。心理健康类系统必须明确边界，所以我设置了普通压力、中度困扰、高风险表达、边界与依赖四类样本。系统在检测到危机表达时，不会继续普通聊天或进入幽默人格，而是触发安全保护回复，提醒用户联系可信任的人、学校心理中心或紧急帮助。同时，系统也会避免做医学诊断，强调 AI 不能替代专业心理咨询。

最后总结一下，本项目完成了一个从前端交互、后端服务、数据库持久化到 AI Agent Pipeline 的完整 Web 应用。它的主要特点有三点：第一，围绕大学生日常情绪支持场景设计，而不是泛化聊天工具；第二，通过 Agent + Skill Pipeline 提升回复的结构性、安全性和可持续记录能力；第三，通过日记、日历和长期反思上下文，把单次对话扩展为连续的情绪管理过程。

当然，系统仍然有需要完善的地方。比如目前语音模式主要依赖浏览器 Web Speech API，完整的服务端语音识别和 TTS 播放还没有全部接通；管理后台的数据也还有一部分是演示数据，后续可以进一步接入真实 PostgreSQL 聚合统计；此外，还可以补充更完整的端到端测试、失败重试和生产监控。

以上就是我的毕业设计汇报，感谢各位老师的聆听，恳请各位老师批评指正。
